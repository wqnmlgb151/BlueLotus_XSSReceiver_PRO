## 2. 架构和兼容约束

- 接收：`index.php → Request → XssRecordService → FileStorage`。
- 管理：`admin.php → api.php → Controller → Service → Storage`。
- JS 模板和我的 JS：Controller 调用 `dio.php`，描述文件经过加密，JS 内容是明文。
- 前端运行 `static/` 中的资源；`src/` 是维护源文件。涉及前端的修改必须覆盖实际加载的产物并记录生成方式，不能只修改源文件。
- 旧记录以十位秒级时间戳命名；前端把 `request_time` 同时当作时间和行 ID，删除、通知、保活及重加密工具均需评估。
- 配置与加密数据必须成套保存。第一阶段不更改加密方式、密钥或登录协议。
- 项目 Token 当前用于分类，不是权限边界。本轮不改成多用户系统，不擅自改变未知 Token 的兼容行为。

## 3. 优先级和实施单元

### P0-A：避免记录覆盖（优先设计，独立发布）

证据：`XssRecordService::saveRecord()` 使用 `request_time` 作为 ID；`FileStorage::save()` 直接覆盖同名文件。不同项目同秒记录也会冲突，写入没有锁和原子提交。

建议方案：将唯一记录 ID 与真实请求时间分离。新记录增加独立 `id`，旧记录读取时以文件名补足 ID，不批量改名、不改写历史时间。新 ID 具体格式在实施前确定，要求路径安全、碰撞处理明确，并能稳定排序。不能以递增请求时间冒充唯一 ID，否则统计和时间展示失真；只加锁也不能消除同名覆盖。

采用两步发布：

1. 先发布兼容版本：支持旧、新 ID 的读取、列举、删除、前端行标识及辅助工具，写入仍保持旧格式。此阶段覆盖问题仍存在，只为建立回滚基线。
2. 完成兼容验证并备份后，再发布使用新 ID 的写入版本。创建记录与更新已有记录要有明确语义；创建使用排他占位或等效防覆盖机制，更新使用同目录临时文件和原子替换。清理失败必须可见。需验证目标 Windows/Linux 文件系统上的实际行为。

预计范围：`app/Storage/*`、`app/Service/XssRecordService.php`、记录 Controller、`src/js/loadxsspanel.js`、通知脚本及对应 `static/` 产物、`keepsession.php`；同时检查 `change_encrypt_pass.php` 的十位 ID 正则和其他文件遍历调用。重加密工具仍默认禁用。

验收：在隔离副本中让 100 个同秒请求跨两个项目并发写入，要求 100 个唯一 ID、100 条可解析记录、时间不失真；所有 ID 可通过 API 读取；删除一条仅减少一条；通知可定位；旧新记录混合的列表、排序、统计、导出和保活读取路径均通过。模拟写入失败，不能覆盖已有有效记录或将半写文件作为有效记录展示。文件数检查与 API 可读数同时执行。

回退：新格式启用后只回退到已验证的双格式兼容版本。原始基线仅接受十位 ID，不能直接回滚并继续承载新数据；详见恢复文档。

### P0-B：支持数组参数并明确异常输入处理

证据：`XssFilter::stripArr()` 将值直接传给 `stripStr(string)`，并未递归；`Request::tryBase64Decode()` 也直接向字符串函数传值。

方案：保留参数结构，对数组递归处理，仅对字符串叶子执行转义和 Base64 判断。明确嵌套层数、异常类型及无法编码字符的处理方式，不默默丢掉整条记录。与前端确认嵌套数据展示方式，避免后端接收成功但界面无法查看。

预计范围：`app/Helper/XssFilter.php`、`app/Helper/Request.php`；只有展示确实不兼容时才扩展对应前端。

验收：普通标量、空值、嵌套数组、数字索引、混合 Base64、中文、非法字符和边界深度；不出现 TypeError，普通请求字段保持兼容，嵌套数据可在详情与导出中核对。所有请求仅发往隔离测试实例。

### P1-A：项目筛选口径一致

证据：`admin.php` 的 `getSearchUrl()` 在空关键词时不传 `project`，统计与导出则带项目参数；旧通知使用全局 `id_list`。

方案：选定项目后，列表、搜索和统计使用同一个项目值，导出继续按当前项目；明确导出覆盖整个项目、不随关键词缩小。保留 API 不带项目时返回全部记录的旧行为。通知本轮保留全局口径并说明，不顺带重写通知机制。清空仍是全局操作，界面必须明确“所有项目”，不得暗示只清空当前项目。

预计范围：`admin.php`，必要时统一 `src/js/loadxsspanel.js` 中重复的 URL 构建逻辑及运行产物。

验收：两个项目分别放入不同记录；切换项目、搜索、清除搜索后，列表和统计始终匹配；导出只含选中项目；无项目参数的旧 API 行为保留；全局清空范围明确。

### P1-B：中文搜索可用

证据：`listRecords()` 在默认 `json_encode()` 的结果上查找关键词，中文会被转义。

方案：首先采用保留 Unicode 的 JSON 编码进行搜索，不扩大到全文搜索系统。单独定义 HTML 实体、原始值和 Base64 解码值的搜索语义，避免借本次修复改写历史数据。

验收：中文、英文、混合字符串、无匹配结果及项目过滤组合均正确；对编码失败提供可观察的错误处理。

### P1-C：消除读取回写，改善失败可见性

证据：`FileStorage::load()` 缺少 `location` 时调用 `save()`；`index.php` 未处理保存返回值，部分入口关闭错误显示，文件操作有错误抑制。

方案：读取时只在返回对象中补足归属地，不持久化；首轮不做批量补全。对保存失败、读取损坏、删除失败建立最小日志与返回约定，日志不包含 Cookie、密钥或完整采集内容，不将内部路径返回客户端。清空操作不得在部分失败时无条件宣称成功。

验收：列表、搜索、统计、导出前后业务数据文件哈希不变；只读目录、缺失 IP 库、损坏记录和写入失败在隔离环境下可被识别，不导致其他有效记录消失。

## 7. 第二批实施记录（2026-10-30，P0-A）

### 方案与实现

- ID 规则集中在 `app/Storage/RecordId.php`：旧格式十位秒级时间；新格式为十位秒级时间加 `-` 和 32 位小写十六进制随机值（128 位）。严格锚定首尾，不接受换行、路径或任意文件名。
- `request_time` 保持原时间语义。读取时以文件名返回 `id`，不改名或回写旧文件；同秒新记录按随机后缀确定排序，不声称具备毫秒到达顺序。
- `FileStorage` 的读取、列举、删除和清空识别双格式。前端行主键改为字符串 `id`，CSV 的 ID 列导出真实 ID；通知继续把完整 ID 传给查询接口。
- `save` 用同目录随机临时文件完成写入，再通过 `rename` 替换；新增 `create` 用 `link` 排他发布，已有目标返回 false，不覆盖。不支持硬链接的文件系统会返回失败，不退回非原子覆盖。临时文件带 PHP 退出前缀，文件名不符合记录 ID 规则，列举不会将其作为记录。
- 保存检查写入长度、刷新、关闭及发布结果；清理临时文件失败记录固定日志。实现保证完成文件的原子可见性，不承诺停电持久性；未加入文件系统 fsync 或目录同步。
- `XssRecordService` 在 `UNIQUE_RECORD_ID_ENABLE=true` 时生成新 ID 并调用 `create`。未配置或 false 保持旧格式和同秒覆盖行为。随机冲突返回保存失败，不覆盖原记录、不修改请求时间。
- `keepsession.php` 已按文件名经 Service 读取，无需改变遍历方式。`change_encrypt_pass.php` 的文件筛选接入统一 ID 校验；脚本仍以 `exit()` 默认禁用，没有执行原地重加密。
