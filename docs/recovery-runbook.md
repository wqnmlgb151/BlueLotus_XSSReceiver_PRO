## 3. 变更前完整备份

1. **识别路径与版本。** 读取实际 `config.php` 中的 `DATA_PATH`、`MY_JS_PATH`、`JS_TEMPLATE_PATH`、`IPDATA_PATH`，解析为绝对路径并核对是否位于项目外。记录所有未提交修改和运行时静态产物。
2. **暂停所有可能写入的活动。** 在入口或 Web 服务层进入维护状态，暂停接收请求、管理员操作、保活调度和其他写入任务；记录停用前状态。仅关闭浏览器或只暂停 `index.php` 不足以建立一致性点：原始基线读取记录也会补写归属地，本轮修复版本虽已去除该副作用，仍须暂停所有业务写入。
3. **等待执行中的请求结束。** 确认 PHP 请求、文件更新和保活进程已停止。维护期间的请求是否排队取决于部署设施；没有持久缓冲时必须记录接收中断可能造成的数据损失。
4. **复制到独立备份位置。** 使用目标系统受支持的备份或文件复制工具，保留相对目录、隐藏文件及必要的权限元数据。不得删除源文件、剪切目录或用目录镜像删除选项覆盖已有备份。
5. **备份完整集合。** 按下面清单逐项核对，包括配置指向的项目外目录。不要只备份默认的 `data/`。
6. **生成并复核清单。** 在停止写入状态下，对源文件和备份副本逐文件比对数量、大小和 SHA-256；记录无法读取或复制失败的文件。只要有未解释差异，备份不能标为成功。
7. **在隔离位置执行第 4 节恢复演练。** 完成前不开始格式变更。成功后记录检查点时间、版本与清单引用，封存备份，避免后续验证改动该副本。

| 必备内容 | 恢复用途 |
|---|---|
| 当前完整应用源码和 `static/`，含本地改动 | 恢复实际部署版本，而非仅远端版本 |
| 实际 `config.php` | 登录配置、路径、项目和解密参数 |
| 实际数据目录中的全部业务文件 | 记录、封禁列表及相关目录规则 |
| 实际 `myjs` 与 `template` 目录 | `.js`、`.desc`、访问规则及用户自定义文件 |
| 实际 IP 数据库 | 归属地解析 |
| `.htaccess` 和 Web 服务配置 | 恢复访问限制、路由及环境行为 |
| 外部调度定义和环境说明 | 按原状态恢复任务 |

`check.pid` 是运行锁文件，不代表业务数据或旧进程所有权。备份可保留其证据副本，恢复时应在确认无旧进程后由运行环境重建，不以复制锁文件替代停止进程。

## 4. 隔离恢复演练

1. 创建与生产不同的非公开恢复目录，使用相同 PHP 版本及所需扩展。复制备份到该目录，保持备份原件不变。
2. 核对恢复副本与备份清单的文件哈希。仅在恢复副本中调整绝对路径；保留解密参数一致，记录每项环境差异。
3. 阻断外部出站连接、关闭邮件和保活调度，限制测试实例只允许维护人员访问。恢复副本中的配置变更仅服务于演练，不覆盖封存备份或生产配置。
4. 确认 PHP 可正常解析，登录与会话可用。先核对磁盘文件，再查看列表和详情；旧版本的首次读取可能补写 `location`，由此产生的哈希变化仅发生在演练副本，并需记录。
5. 选择不同项目、不同日期和新旧格式记录核对字段；对全部记录做可读性检查，报告损坏或无法解密的数量，不能只依据抽样宣布完整恢复。
6. 核对 JS 内容和描述配对、封禁列表可读取、项目配置、统计和导出可用。保活只使用受控本地测试目标，不能重放真实 Cookie 到外部系统。
7. 在演练副本单独创建合成记录，验证新增、查询、删除及并发场景；测试文件不得进入正式恢复集合。若需上线，应从封存备份重新创建干净恢复副本。
8. 记录耗时、失败项、差异及是否满足约定 RPO/RTO。失败时保留原服务状态与备份，修正预案后再演练。

- 测试和发布使用不同的数据目录，临时调试配置不进入生产。

## 6. 故障回滚决策

| 故障场景 | 首选处理 | 必须保留的内容 |
|---|---|---|
| 仅代码或前端回归，数据格式与加密配置未变 | 暂停写入，回退代码和静态产物，保留现有有效数据 | 故障版本副本及新增数据 |
| 已启用新记录 ID | 回退到双格式兼容版本，保留全部新旧记录 | 新格式数据、兼容读取代码 |
| 文件损坏或误删除 | 封存当前目录，在新目录恢复一致备份并对账新增数据 | 当前文件、日志、备份清单 |
| 配置与密文不匹配 | 先检查路径和配置配对；使用匹配的配置与数据集合 | 原密文及所有候选配置副本 |
| 加密迁移部分完成 | 停止迁移，封存混合状态，从迁移前成套备份恢复并隔离后续新增数据 | 迁移日志、格式清单、旧新配置和密文 |

原始基线及第一批版本仅识别十位记录 ID，第二批已增加双格式读取与重加密文件筛选。新格式启用后，直接回退到原始基线或第一批会使新记录不可见，应使用第 11 节双格式兼容检查点。没有目标环境验证通过的兼容版本时，应继续维护状态，保全数据并修复兼容读取；不得把“看不见”当作“没有数据”。

## 7. 正式恢复步骤

1. **隔离故障。** 暂停接收、后台写操作和外部任务，等待在途请求结束；记录故障时间和最后已知正常时间。
2. **封存现状。** 复制当前代码、配置和全部数据到新的故障保全目录，生成清单。即使当前数据损坏，也不能直接覆盖或删除，以免丢失备份之后的新记录。
3. **选择恢复点。** 根据上表决定仅回退代码还是恢复完整集合。核对版本与数据格式兼容、加密参数配对，确认恢复点到故障时间之间的数据窗口。
4. **在新目录恢复。** 从完整备份复制到新目录，核对哈希、文件数量、权限和实际配置路径；不得把旧备份直接覆盖正在使用的目录。只回退代码时，将现有有效数据绑定到兼容代码，避免误恢复旧数据。
5. **对账新增数据。** 对比故障保全副本和恢复集合的 ID、哈希与记录内容。相同路径但哈希不同的文件作为冲突单独保存，禁止静默覆盖。不同密钥或格式的文件不得直接混放；先在隔离副本中用对应配置读取，制定并验证转换后再合并。
6. **验证恢复集合。** 执行第 4 节的读取和业务检查。所有写入探测只在该集合的另一个副本进行，或使用有明确清单的合成记录并确保它们不进入正式集合。与基线对比时注明哪些变化来自正常新增、回写或对账。
7. **切换服务。** 保持流量暂停，使用部署环境既有的发布切换方式指向验证后的代码和数据；检查 PHP 配置、缓存刷新及文件权限。不要用递归删除或未核实路径的移动来实现切换。
8. **分步恢复。** 先开放管理员检查，再开放数据接收；确认写入与读取正常后，按先前状态恢复邮件和保活任务。需要重新登录时建立新会话，不复用来源不明的旧会话文件。
9. **观察并记录。** 在预先约定的观察窗口内核对接收计数、唯一 ID、读写错误、后台展示和任务执行。记录新增数据的保留、冲突、损坏与未恢复数量，并持续保留回退目录。

## 8. 加密恢复特别说明

`change_encrypt_pass.php` 以 `exit()` 默认禁用，且采用原地逐文件改写；它不是事务性恢复工具。本轮不启用、不运行，也不将其作为常规回滚步骤。

若未来需要加密迁移，应另行设计：离线副本转换、逐文件解密和结构验证、迁移清单、失败中止及原件保留。完成转换前不得独立替换生产密钥。恢复时优先恢复成套配置与密文，而不是对状态不明的数据反复重加密。

## 9. 完成标准与留档

只有以下项全部满足，才能宣布恢复完成：

- 代码、配置、数据格式配对，全部记录可读性检查已完成，损坏项已列明。
- 文件数量与哈希差异都有解释，备份后新增数据已经对账，无静默覆盖。
- 登录、项目列表、详情、搜索、统计、导出、JS 内容与描述检查通过。
- 在合成数据副本验证接收与删除，正式实例恢复后实际接收可持续读取。
- 邮件、保活等任务仅恢复到明确记录的原状态。
- 记录实际恢复耗时、数据损失区间和未解决项，并与约定 RPO/RTO 比较。

恢复成功不自动授权清理备份。备份和故障保全副本的保留期限由维护方另行确定，后续清理需确认不再承担恢复用途。
